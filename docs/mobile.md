# Mobile MVP

Android and shared Kotlin Multiplatform logic are in `composeApp/`; `iosArm64` and `iosSimulatorArm64` remain configured. The existing Master Coffee teal palette, Montserrat fonts, drink/cafe images, categories, sizes, sugar, takeaway/dine-in, temperature, syrup/essence/milk options, RU/KK/EN and light/dark/system themes are retained. Known catalogue translations were moved from the original dictionary into resource XML; newly authored catalogue content uses its server-provided text until translations are supplied.

## Source migration map

The original 3,334-line `App.kt` mixed Compose, state, catalogue fixtures and network writes. Firebase usage was: `stories` documents (`url`, `active`) read and uploaded from an in-app administrator screen; `orders` collection written after local success, then read without ownership filtering for history and receipt count; `Firebase.auth.currentUser.uid` used for display with a fabricated fallback ID; Android Firebase Storage used for profile-image uploads while iOS returned an empty string. Cloudinary used a public cloud/preset URL for story uploads. Local preferences contained `isLoggedIn`, profile fields, theme/language, cart and story caches. Any four OTP digits enabled local login. No live Firebase data was accessed during replacement.

These callers have been replaced with the Go API, server sessions and owner-scoped history/loyalty. Google Services, Firebase Auth/Firestore/Storage, coroutines-play-services, Cloudinary upload code, Peekaboo, Kamel and the common CIO engine were removed. One Coil image loader remains for server story/product images; `/uploads/` paths resolve against the API origin and bundled images are mapped from stable string keys in the UI. Food products retain the server `is_drink` flag and do not expose beverage-only sugar, temperature or addon controls. There is no profile photo uploader, in-app administrator, MC Coins, referral, promotional redemption, fake OTP or customer payment-confirmation control in this MVP. Staff/admin operations are in the web cabinet. The previous user whitespace change is retained in `docs/preexisting-user-change.patch`; the original source is backed up outside the checkout.

## Layers and session lifecycle

`domain/` holds immutable business models and the repository contract. `data/` holds separate serializable DTOs, Ktor, public catalogue/cart persistence and platform services. `presentation/` holds a ViewModel/StateFlow, resource-backed copy and screens. `App.kt` only composes dependencies, theme and lifecycle observers. There is no global mutable order list or GlobalScope.

Android uses Ktor OkHttp; iOS uses Darwin. Requests have connection/socket/request timeouts, no credential logging and no redirect forwarding. The client closes with its ViewModel. A saved token is validated by `/auth/me` before displaying an account. Android saves only AES-GCM ciphertext in private preferences with a non-exportable Android Keystore key; backups are disabled. iOS uses a `kSecClassGenericPassword`, `WhenUnlockedThisDeviceOnly` Keychain item. Ordinary settings contain UI preferences and public catalogue data. Account carts/recovery records use checked synchronous Android private preferences commits or separate device-only iOS Keychain accounts. Logout erases tokens, cart, pending keys, history, loyalty and selected order and cancels account work. Revocation is attempted server-side; an offline logout still removes the local credential, while the unreachable server session expires naturally.

`CoffeeEnvironment` is loaded on a background dispatcher, including engine and store constructors. `BackgroundStorage` serializes every Settings, Keystore, Keychain, cart and recovery operation with a mutex on that dispatcher. The low-level synchronous storage APIs retain their durability without blocking Compose/Main. There are no disk reads in the ViewModel's state initializer. Unit tests inject a test dispatcher; instrumentation stores fail immediately if accessed on Android's main thread.

Authentication and account requests carry a generation guard. Logout increments it, cancels old jobs, clears account UI immediately and disables a new login until serialized local erasure finishes. A cancellation-resistant late response cannot establish the old account or repopulate its state. Loading flags are set before launching requests, so double taps are rejected in the same UI turn. Storage failures are visible errors rather than uncaught button-handler exceptions. Comments are debounced for typing, flushed before quoting, and all request flows have bounded deadlines.

The mobile application accepts customer accounts. Staff/admin sign-in directs the user to the web cabinet, never persists the returned token and attempts bounded revocation. A restored account whose role changed is cleared locally. Server authorization remains authoritative.

The repository explicitly closes both its HttpClient and its platform engine. [Ktor 2.3.9 source](https://raw.githubusercontent.com/ktorio/ktor/2.3.9/ktor-client/ktor-client-core/common/src/io/ktor/client/HttpClient.kt) sets `manageEngine=false` for `HttpClient(engine)`, so closing that client alone does not close an externally supplied engine. A client test verifies engine-job completion and repeated repository closure.

Public catalogue cache is scoped by cafe. It can be shown offline with an explicit stale-cache message. Cart changes are persisted per account. Quotes and successful orders are never fabricated from cache. Before creating an order the client durably persists `{quote_id, idempotency_key}` using a checked synchronous Android preferences commit or a separate account-scoped iOS Keychain item; ordinary asynchronous settings are not used for this recovery record. An uncertain network result retains this exact pair and the cart, including after process death. Retry recovers the server's original order. Only a successful server response clears the cart. A changed/expired quote requires a new server calculation and explicit confirmation. Price amounts and loyalty are always server supplied in whole KZT; timestamps arrive in UTC and are displayed in the device timezone.

Active orders poll every 5 seconds while the screen lifecycle is started. Preparation and payment are displayed separately. A QR uses only the server payload and expiry. The customer can refresh an unpaid QR or cancel a created unpaid order; only authenticated staff can record payment or handoff. The server is authoritative about every transition.

Selected tab, cafe and order reference are stored as account-scoped `SavedNavigation`; server data is fetched again after process recreation. A pending request restores the cart/recovery screen. Android system Back and the common toolbar return from tabs to the menu; modal Back closes the dialog. Product selection, size, sugar and addon drafts use `rememberSaveable` across Activity recreation. Passwords deliberately are not saved in instance state. Logout removes account navigation too.

`CoffeeShell` restores the original 320 dp side drawer, avatar ring, separate language/theme sheets and floating 32 dp rounded navigation bar with an 8 dp shadow. Its five destinations use the existing ViewModel navigation; drawer and sheet state are scoped to the account. Menu, cafe and product surfaces reuse the original rounded-card/shadow treatment, Montserrat and horizontal story thumbnails. `BrandLogo` uses the original horizontal artwork; branding and unknown/failed image fallbacks take their tint from the active palette, while successful product/cafe photos retain their original colors. This visual shell changes presentation only; quotes, loyalty, recovery and order transitions remain server supplied. Device evidence captured before this revision verifies business flows, not the revised appearance; the final visual/instrumentation results are recorded separately.

Existing `durable_orders_v1` Android keys and iOS `cart:<user>`/`pending_order:<user>` Keychain accounts remain compatible. Older `mvp.cart.<user>`/`mvp.pending.<user>` records migrate before legacy removal. A durable per-account migration marker prevents an old asynchronously removed record from resurrecting after successful checkout or logout. Android commits canonical records and the marker atomically; iOS writes canonical items before its Keychain marker. Malformed cart/recovery records surface a storage error and remain intact for diagnosis; they are not silently replaced with an empty cart. Public catalogue caches may safely be discarded when malformed.

## API address and build

Use JDK 21, Android SDK 36 and Gradle wrapper. The default debug URL is `http://10.0.2.2:8080/api/v1` for Android Emulator. Override with a Gradle project property:

```powershell
.\gradlew.bat :composeApp:assembleDebug :composeApp:testDebugUnitTest
# USB phone:
adb reverse tcp:8080 tcp:8080
.\gradlew.bat :composeApp:assembleDebug -PmasterCoffeeApiUrl=http://127.0.0.1:8080/api/v1
# Phone on the same LAN; use this machine's actual address:
.\gradlew.bat :composeApp:assembleDebug -PmasterCoffeeApiUrl=http://192.168.1.10:8080/api/v1
# Release must receive a real HTTPS endpoint:
.\gradlew.bat :composeApp:assembleRelease -PmasterCoffeeApiUrl=https://YOUR-API-HOST/api/v1
```

Local HTTP is allowed by Android's manifest only in debug; a release client also rejects a non-HTTPS URL. `validateReleaseApiUrl` fails release tasks without an explicit HTTPS `masterCoffeeApiUrl`; no production endpoint is bundled. R8 and resource shrinking are enabled with library consumer rules and retained diagnostic line information. Release signing/distribution is not configured; the local release output is unsigned. A compile check against `https://localhost/api/v1` proves build configuration only and is not a deployed endpoint or a release runtime test. The debug profile shows its compiled API address. The debug APK is `composeApp/build/outputs/apk/debug/composeApp-debug.apk`.

iOS uses `MasterCoffeeAPIURL` from Info.plist, expandable via the `MASTER_COFFEE_API_URL` Xcode build setting. Debug falls back to `http://127.0.0.1:8080/api/v1` for a local iOS Simulator; release requires an explicit real HTTPS value. Local networking is permitted in ATS, but arbitrary insecure remote loads are not. Keychain operations run through the shared background storage boundary. No macOS/Xcode was available on this Windows host: iOS compilation, native storage migration, Darwin/UI runtime behavior and profiling remain unverified.

Keychain ownership and collection bridging were reviewed against [Kotlin Objective-C interoperability](https://kotlinlang.org/docs/native-objc-interop.html), [Kotlin Platform opt-in](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.native/-platform/), [Apple CFBridgingRetain](https://developer.apple.com/documentation/foundation/cfbridgingretain(_:)), [Apple SecItemCopyMatching](https://developer.apple.com/documentation/security/secitemcopymatching(_:_:)), and [device-only accessibility](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly). This source review does not substitute for a native build or device test.

## Verification

Client tests cover successful quote/confirmation, preserving cart on failure, durable identical-key retry after timeout and process recreation, retaining recovery data if local cleanup fails after server success, explicit fresh review after price changes, expired session validation, logout/account isolation and cancelled late responses, offline cache, lifecycle polling including cancellation of an in-flight request, API identifier-only quote serialization, typed errors/timeouts and production HTTPS enforcement. Android compile/APK succeeded. See `docs/verification.md` for the final count and emulator status. The first attempt to execute the new unit suite was interrupted by host disk/pagefile exhaustion; after releasing the build processes, the complete suite and APK build passed using a 768 MiB single-use Gradle JVM, in-process Kotlin and a 128 MiB test JVM.

UI uses scrollable forms/dialogs, safe insets, keyboard padding, flexible text heights, labelled controls and a single menu column on narrow screens or increased font scale. These implementations still need actual small-screen, font-scale and TalkBack review before pilot; no claim of certified accessibility is made.

## Android instrumentation

`assembleDebugAndroidTest` builds `composeApp/build/outputs/apk/androidTest/debug/composeApp-debug-androidTest.apk`; `connectedDebugAndroidTest` runs it using AndroidJUnitRunner, package `kz.master_coffee.app.test`. Test sources are under `src/androidInstrumentedTest/`. The debug-only `MobileTestActivity` hosts the actual `CoffeeApp`/ViewModel with managed stores; tests never clear a real user's account or Keystore. Managed cases cover sign-in, cafe/drink configuration, dialog recreation, server quote confirmation, status, Back, logout/isolation and network recovery.

`MobileBackendJourneyTest` is skipped unless runner argument `masterCoffeeLiveApi` is supplied. Also provide `masterCoffeeStaffEmail` and `masterCoffeeStaffPassword` for a development staff account assigned to cafe 1. It registers a unique verification customer, drives customer UI against the real API, performs authenticated cashier QR lookup/payment/status changes, then waits for actual client polling, completion and loyalty. It emits `masterCoffeeLiveOrderComplete=true` only after the complete scenario. Screenshots are written to the app's external `files/verification` directory without logging credentials.

`MainActivityLaunchTest` separately exercises actual `MainActivity`/`App` dependency wiring, cold auth display, email draft after rotation and background/resume. Enable it with `masterCoffeeLaunchSmoke=true` only on a clean verification device. It performs no login, logout, data clearing or account switching. The main Activity and live journey screenshots are separately named. Exact executed checks and device identity belong in `docs/verification.md`; compiling a test APK is not proof that instrumentation ran.

During the prior local verification attempt, an isolated `MasterCoffeeVerification` AVD was created under ignored `artifacts/mobile/avd/`, preserving the user's existing AVD. Android Emulator 36.4.9 forced a 6 GiB userdata partition and initially required 7.2 GiB free host disk. A factory-backing-image bootstrap started the guest, but ADB remained offline; later launch failed the host disk-space check with about 1 GiB remaining. The original user AVD was not wiped or deleted. This historical attempt supplied no UI evidence; current CI/device results are recorded separately in `docs/verification.md`.
